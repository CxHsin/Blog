在前天，我又重复看了[matt和poteto的直播视频](https://www.youtube.com/watch?v=MN9dGgmLyso)，在开场，poteto分享过自己一个月向生产环境交付约 2000 个 PR 的经历。后来他在 [pstack 指南](https://x.com/poteto/status/2094457600259842065)里也写到，pstack 让他每月能以较高的信心向生产环境交付 2,000 个 PR。

这是一个诱惑性的开场，因为就我们这类程序员而言，产出是非常重要的。我想我们现在大多数人的开发方式就是：双击 Codex / Claude Code，点开一个聊天框，然后开始 chat。然而这种方式意味着，我们的产出是严格与注意力绑定在一起的，我们不关注，也就无法产出。

这同时又引出了另一个问题：PR 的质量如何保证呢？如此大量的 PR，仅靠人来审阅是绝对不可能的。

[Faros AI 的团队](https://www.faros.ai/research/ai-acceleration-whiplash)发布过一份报告：自从我们在一、二月份陆续开始使用这些 AI 编程工具以来，Pull Request 的评审质量大幅下降。

- 评论更多了、评论更长了，还有大量 PR 根本没有经过评审就被合并。
- 事故大幅增加。
- 每位开发者对应的 Bug 数量大幅增加。

所以，问题不是“怎样让 Agent 写更多代码”，而是“怎样让 Agent 写得快，同时不把代码库写坏”。

我会从两个方面来讲：一方面是为什么 AI 明明 benchmark 跑分这么高了，依旧会产生大量 AI slop；另一方面，我会结合 poteto、Dex 和其他项目的实践，讲讲如何通过 repo harness 在维持质量的前提下提高产出。

这里的 **repo harness**，不只是代码本身，而是让 Agent 能理解仓库、遵守边界、执行任务并验证结果的一整套工程环境：代码结构、上下文、工具、测试、验证流程和维护机制。

## 一、软件工厂：瓶颈从构建转移到了验证

既然讲到提高产出这件事，就绕不开软件工厂。近几个月，X 上关于熄灯工厂（Agent 工厂）的讨论一直非常火爆，也有不少实践。然而现在回头看，大部分都是炒作大于实际。

在 AI 之前，软件工厂的核心流程大致是：人决定要构建什么，任务进入 Linear / Jira 等跟踪系统，有人领取任务并完成构建，然后创建 PR，经过自动检查和人工评审，最后发布到生产环境，再根据监控和用户反馈继续迭代。

![Both build and review take hours or days](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/raw/main/images/software-factory-leverage-wm-shadow.png)

Agent 式软件工厂的变化是：从“人来构建”变成“Agent 来构建”。构建时间可以从数小时或数天降到数分钟或数小时，但 Review 仍然需要数小时或数天。仍然需要有人阅读代码、测试改动，并判断它是否值得合并。

于是很多团队会继续加速 Review：使用 Agent 式 Code Review 发现风格问题、Bug 和安全问题，使用浏览器或计算机操作 Agent 做回归测试，甚至把事故和用户反馈也路由进工厂。

这条路线看起来很合理，但它容易忽略一个问题：**Agent 让“写代码”变快了，却把瓶颈转移到了“判断代码是否正确、是否值得合并”。**

如果仓库本身无法提供足够的上下文和验证能力，Agent 写得越快，Review 压力就越大，代码库也会以更快的速度退化。

## 二、模型会随时间降低 Codebase 质量

为什么模型明明几个月来强了那么多，却仍然无法维护好 codebase 呢？

- 解决一次性问题，或者凭感觉做一个全新的营销网站？是的，好多了。
- 随时间推移改善代码库质量？据我所知，没好多少。

说实话，我看了很多资料，但现在确实没有好的 benchmark 来衡量模型维护代码库的能力。

首先，如何让模型更擅长编程（详细讲解可以看看 [Calvin French-Owen](https://x.com/calvinfo) 在 [AI Council](https://www.youtube.com/watch?v=q-ntX4DLW_c) 的演讲和[Dex 做的动画](https://github.com/user-attachments/assets/25c45e29-ebf7-4ce7-9b57-969cdf305e2e))？

简单来说就是：

1. 让 Agent 解决一个问题（例如：修复我的测试），生成一些编码 Agent 轨迹；
2. 根据某些标准给这些轨迹打分（验证器）；
3. 更新模型权重，让好的轨迹更有可能出现，让坏的轨迹更不可能出现。

然后在数周或数月的时间里，把这个过程重复数百万次。

然而，这些过程中的“评分”往往带有一种随意的单一维度。

### 糟糕的设计不会受到惩罚

以 [SWE-bench Multilingual](https://huggingface.co/datasets/SWE-bench/SWE-bench_Multilingual) 为例。任务很小，每个大约需要十五分钟，来自 Redis、jq 和 Django 等开源仓库。奖励是 0 或 1，依据的是：

- `FAIL_TO_PASS`——你是否修复了被要求修复的问题？
- `PASS_TO_PASS`——你是否在修复它的同时没有破坏其他东西？

那么仅从这两个维度可以判断模型变强了吗？不能。这只能表达：模型是如何得到正确答案的并不重要。只要测试通过，ok，我们胜利了，但**代码库可维护性恶化不会受到惩罚**。

这只会导致：**每次变更都局部合理，但系统整体在退化。**

而什么是好的设计呢？

- **复用**：是否用了仓库里已有的抽象，而不是自己造一套
- **范围**：是否只改了该改的东西，没有顺手动别的
- **方向**：依赖方向对不对，有没有让底层模块反过来依赖上层
- **简洁**：有没有为了一个边缘 case 加了不必要的分支、参数、配置
- **兼容**：有没有改动公共接口但没检查其他消费者
- **意图**：改动的原因是否清楚，下一个人能不能理解为什么这么做

### 验证质量比“测试通过”难度高了几级

运行测试，大约几秒钟就能得到干净的通过或失败结果。这就是为什么强化学习可以运行数百万次循环，来优化每次模型生成。

但糟糕架构的代价函数，是以数周、数月，甚至数年为单位衡量的。

> 测试在几秒钟内给你反馈，但糟糕架构的代价函数以数周、数月甚至数年为单位衡量。

事实上，很多人都发现了这个问题，并在努力解决：

- [SWE-Marathon](https://www.swe-marathon.org/)（Abundant AI）：类似“克隆整个 Excel，包括每一个功能”的约 400 小时任务；使用复合奖励通道，而不是单一的通过/失败比特；
- [DeepSWE](https://deepswe.datacurve.ai/blog/deepswe)（Datacurve）：在真实世界中从未实际构建过的大型开源仓库任务，因此按构造来说，它们不可能已经存在于训练集里（解决了数据污染问题，但没有解决质量问题）；
- [Frontier Code](https://cognition.com/blog/frontier-code)（Cognition）：使用多 PR 任务，并采用了一个巧妙的办法来确定性地评估质量——如果模型编写的测试在应用补丁之前的代码上不会失败，就会受到惩罚（如果你从未听说过[变异测试](https://en.wikipedia.org/wiki/Mutation_testing)，那你即将发现一个很有趣的东西）。它还会**让一个评审模型检查差异中的代码质量规则**。

设想：如果模型能够可靠地区分好代码和坏代码，它可能一开始就已经写出了好代码；但可维护性没有快速的裁判，因此我们无法在强化学习过程中为它提供奖励。

或许未来某一天模型会学会这一点，那么程序员或许就可以停手了，我们就可以做更高抽象的工作了。

但在当下，我们不能等模型自己学会维护代码库。我们需要做的是：**让仓库本身提供模型训练时缺失的上下文、约束和验证。**

## 三、什么是 repo harness

那么在当下，如何解决上面由于模型而导致的问题呢（好吧，有点自己不行怪他人的感觉）？

我认为，就是去建设、维护好一个 repo harness。

我之前听过一句话：

> AI agent 编程的一切问题，都是上下文的问题。

但只有上下文还不够。Agent 不只需要知道该做什么，还需要能执行、能检查，并能留下证据。因此，repo harness 至少包括三件事：

1. **上下文**：让 Agent 知道系统现在是什么样、什么不能做、这次要做什么；
2. **约束**：让错误尽早撞到类型、lint、测试或编译器，而不是等人在 Review 时发现；
3. **验证**：让 Agent 能运行应用、检查结果，并证明自己的改动正确。

### 上下文的类型

我认为在一个 codebase 中，关键就在于维护四类上下文：

**1. 事实性上下文** — 系统现在长什么样

- 入口在哪、调用链怎么走、数据从哪来到哪去
- 已有哪些工具函数、抽象、类型
- 解决的问题：防止 Agent 重复造轮子、接错接口

**2. 约束性上下文** — 什么不能做

- 哪些接口是公共契约不能破坏
- 哪些模块之间不能产生依赖
- 哪些行为是兼容性要求，看着像 dead code 但不能删
- 解决的问题：防止 Agent 改坏系统边界

**3. 意图性上下文** — 这次任务到底要什么、不要什么

- 要解决的问题是什么
- 明确不在范围内的东西是什么
- 为什么选择这个方案而不是另一个
- 解决的问题：防止 Agent 扩大范围、顺手重构

**4. 证据性上下文** — 怎么证明做完了

- 跑什么测试、检查什么类型、看什么日志
- 如何进入功能、复现问题、截图、录屏或采集 trace
- 哪些行为需要人工确认
- 解决的问题：防止 Agent 自己宣布“完成”但实际没验证

大多数 Agent 使用场景里，只提供了第一种——把相关代码丢进去，让它改。后三种几乎完全缺失。

这就导致了以下常见 bad case：

| Bad case               | 缺的是哪种上下文                      |
| ---------------------- | ------------------------------------- |
| 没有复用已有抽象       | 事实性（不知道已有什么）              |
| 改动了范围外的代码     | 意图性（不知道边界在哪）              |
| 破坏了公共接口         | 约束性（不知道什么不能动）            |
| 增加不必要的分支和参数 | 意图性 + 证据性（不知道“够了”的标准） |
| 自称完成但没跑验证     | 证据性（不知道怎么证明）              |

### 上下文放在哪里

关键不是把所有上下文都塞给 Agent，而是让不同类型的上下文有稳定的位置，并能在对应阶段被拉取。

| 上下文类型   | 典型载体                                    | 什么时候加载       |
| ------------ | ------------------------------------------- | ------------------ |
| 事实性上下文 | 目录结构、类型、入口文件、Feature Map       | 开始理解任务时     |
| 约束性上下文 | lint、类型边界、依赖规则、公共接口测试      | 修改代码时         |
| 意图性上下文 | issue、设计文档、任务说明、非目标           | 开始实现前         |
| 证据性上下文 | 测试、验证 CLI、截图、录屏、trace、验证报告 | 修改后和提交 PR 前 |

所谓优秀的 repo harness，是设计一个结构，让 Agent 在不同阶段能**按需拉取**对应类型的上下文，并且在出错时尽早得到反馈。

## 四、好的 codebase 长什么样

[matt和poteto的直播视频](https://www.youtube.com/watch?v=MN9dGgmLyso) 有一句话令我印象深刻：

> 随手改东西也不会搞砸的，就是好的 codebase。

但这不是说代码简单或功能少。它说的是一种性质：**局部可推理性**。

意思是：当你只看一个模块的代码和它的直接依赖时，你就能大致确定：

- 改这里会影响什么
- 不会影响什么
- 怎么验证改对了

如果做到这一点，不管是人还是 Agent，都不容易搞砸。反过来，如果改一个组件之前需要先理解整个系统的状态流转，那谁来改都危险。

进行提炼的话，可以得出六个特性。

**1. 入口清楚**

一个新人（或 Agent）拿到仓库，能快速回答：

- 应用从哪里启动
- 一个请求从哪里进入
- 功能从哪里注册

如果回答这些问题需要在十几个文件之间跳转，入口就不清楚。poteto 视频里 Dune 的五个名词（Feature、UI、Client、Host、Entrypoint）就是在做这件事——用固定的词汇把入口结构化。

**2. 边界显式**

模块之间的边界不能只存在于开发者的脑子里。好的 codebase 会用以下至少一种方式把边界变成可检查的东西：

- 目录结构（`feature/`、`ui/`、`client/`、`host/`）
- 类型接口（跨模块通信必须经过定义好的类型）
- lint 规则（禁止某些模块之间的 import）
- 编译时约束（包的可见性、依赖方向）

关键不是用哪种方式，而是边界必须**在代码里能撞到**，而不是写在文档里让人自觉遵守。

**3. 只有一种推荐路径**

如果仓库里做同一件事有三种方式，Agent 会随机选一种——通常是它上下文窗口里最近看到的那种，而不是最正确的那种。

好的 codebase 对常见操作有明确的默认做法：

- 错误处理用什么模式
- 状态管理用什么方案
- API 调用走什么层
- 测试怎么组织

不需要只有唯一的方式，但需要有一个**显然是首选**的方式。

**4. 失败路径和成功路径同样清楚**

很多 AI 生成的代码只实现了 happy path。这不完全是 Agent 的错——如果仓库里的错误处理本身就不一致，Agent 没有参照物。

好的 codebase 会让你看到：一个异步操作不只有 `loading → success`，还有 `error`、`timeout`、`cancelled` 各自怎么处理。

**5. 旧代码的意图可见**

最危险的不是复杂代码，而是**看起来可以删掉但实际承担了隐含责任**的代码。

好的 codebase 里，注释解释的是“为什么”而不是“做了什么”：

```ts
// 不能直接用 fetchUser()，因为它不处理 token 过期的重试，
// 而这个路径会在后台 job 里跑，没有用户交互来触发重新登录
const user = await fetchUserWithRetry(userId)
```

这种注释对 Agent 的价值远大于 `// 获取用户信息`。

**6. 可验证**

好的 codebase 不只让人看懂，也让 Agent 能证明改动正确。

“测试通过”只是最低要求。对于真实应用，Agent 还需要能够启动应用、进入目标功能、复现问题、执行用户路径，并留下证据：日志、截图、录屏、性能 trace 或机器可读的检查结果。

如果每次都必须由人手动打开应用确认，Review 仍然会是瓶颈。

把这六条综合起来，判断一个 codebase 是否“好”的标准可以压缩成一个测试：

> 一个不了解项目历史的人，只通过仓库中的结构、类型、测试、工具和少量文档，能否完成一个小型改动、验证它，并且大概率不破坏其他东西？

如果能，这个 codebase 就天然适合 Agent。如果不能，问题不在 Agent，在 codebase。

## 五、让 Agent 能验证自己的工作

poteto 在 [pstack 指南](https://x.com/poteto/status/2094457600259842065)里，把 verification skill 视为工具箱里最关键的技能，甚至把它当作关键基础设施。

这里的验证，不是让 Agent 跑完测试后说一句“已完成”，而是让它能够自己闭环：修改代码、运行应用、检查结果、发现问题、继续修复，直到拿到足够的证据。

一旦这个闭环成立，人就不再需要盯着 Agent 的每一步操作。

### 验证要接触真实应用

测试只能证明代码在测试环境里成立，不等于用户路径一定成立。

Agent 理想情况下应该能做到人手动开发时会做的事情：

- 启动开发环境
- 准备测试数据，比如 seed 一个开发数据库
- 处理登录、测试用户、测试或 staging 环境的 API
- 操作真实界面
- 截图、录屏
- 查看日志
- 采集性能 trace

不同技术栈的实现方式不同。Web 或 Electron 应用可以使用 Chrome DevTools Protocol（CDP），iOS 应用可以利用 simulator。如果当前技术栈缺少足够丰富的调试运行时，就需要额外开发工具，比如基于 lldb 的工具，或者在开发环境中运行的 sidecar。

poteto 甚至提出：为了让 Agent 能够高效验证工作，值得构建自己的调试工具，甚至重新考虑技术栈。技术栈越难调试和控制，Agent 就越难高效工作。

### 给工具，不只给文档

pstack 里有一个原则叫 **Build the Lever**：给 Agent 工具，而不只是 Markdown。

不要只在文档里告诉 Agent “打开设置页，再点击某个按钮”。更好的方式，是给它一个小型 CLI，把常见的开发和验证动作变成可执行命令：

```bash
app-dev seed --user admin
app-dev open settings/billing --json
app-dev screenshot --name billing-page
app-dev trace startup --json
```

这样做有两个好处：

1. Agent 不需要每次写一个一次性的脚本去点击页面，可以节省 token；
2. 验证方式变得可复现、可测试，也更容易维护。

一个对 Agent 友好的 CLI 应该具备这些特点：

- API 易于组合，可以参考 John Ousterhout 的深模块思想
- 有潜在破坏性副作用的命令提供 `--dry-run`
- 用子命令逐步暴露功能，而不是一次性展示全部能力
- 错误信息清楚，并告诉 Agent 下一步应该怎么做
- `--help` 足够完整
- 输出机器可读的结构，比如 JSON

这一步把“证据性上下文”从一段文字说明，变成了 Agent 可以直接调用的工程设施。

### Feature Map：功能的压缩索引

随着应用越来越复杂，Agent 需要更多帮助来找到功能并与之交互。poteto 的做法是建立 **Feature Map**：一份面向 Agent 的功能地图，记录应用里有哪些功能、它们做什么，以及从用户视角如何进入。

一个可能的目录结构是：

```text
references/features/
├── README.md
├── billing.md
├── settings.md
└── onboarding.md
```

`README.md` 是整张地图，提供主要功能的高层概览和链接；每个 feature 文件记录更具体的信息：

```markdown
## Sub-features

## How to get there

## Driving with harness

## Gotchas
```

Feature Map 很适合和前面的上下文模型对应起来：

- `Sub-features` 和 `How to get there` 是事实性上下文；
- `Driving with harness` 是证据性上下文；
- `Gotchas` 是约束性上下文。

poteto 把 Feature Map 看作一种“物化记忆”。代码是团队决策的最终投影，而 Feature Map 是这份投影的压缩索引。它不是新的事实来源，而是帮助 Agent 更低成本地找到事实、到达功能并完成验证。

## 六、前置对齐：减少返工，也减少 Review

验证解决的是“怎么证明做对了”，但还有一个更早的问题：“到底什么叫做对了？”

这就是意图性上下文。它通常不是从代码里自动出现的，而是来自前置对齐。

Dex 在[为什么软件工厂会失败](https://github.com/humanlayer/advanced-context-engineering-for-coding-agents/blob/main/wsff.md)里提到，团队几十年前就会通过规划、架构提案和迭代规划来减少返工。他的估算是：前期花约一小时规划，可以减少返工，并把 Review 从 6 小时缩短到 20 分钟。

在 Agent 编程中，这件事同样重要。可以把前置对齐拆成四个阶段：

1. **产品评审**：要解决什么问题？成功如何衡量？
2. **系统架构**：服务、接口、数据和存储如何交互？
3. **程序设计**：模块边界、抽象和关键接口是什么？
4. **垂直切片**：先打通一个最小可运行路径，再逐步扩展。

当然，不是每个任务都需要完整流程。小任务可以直接完成，中型任务可以把产品和系统设计放进同一份计划，大型任务再走完整流程。

前置对齐本质上是在生产意图性上下文。是为了让 Agent 在开始写代码前就知道：

- 要解决什么问题
- 哪些东西不在这次范围内
- 为什么选择这个方案
- 做到什么程度算完成
- 最后要提供什么证据

这样，Review 就不再是从零开始理解 Agent 做了什么，而是检查它是否按照已经对齐的意图和标准完成了任务。

## 七、扩大产出：先闭环，再并行

很多人想提高产出，第一反应是多开几个 Agent，或者使用 worktree 并行。但如果 Agent 不能可靠验证自己的工作，并行只会制造更多待 Review 的 PR。

真正的顺序应该是：

```text
验证能力可靠
→ 单个 Agent 能把任务推进到接近可合并状态
→ 人不再需要盯着每一步操作
→ 并行运行更多 Agent
→ 接入定时任务、自动化和事件触发
```

poteto 推荐使用云端 Agent，而不是在本地大量使用 worktree。原因是云端 Agent 有独立的机器和完整运行环境，可以安装依赖、运行应用、截图、录屏，并像真实用户一样与应用交互；同时也避免本地机器被大量 worktree 和进程占满。

在验证闭环成立后，产出才会真正扩大。比如：

- **构建新功能**：要求 Agent 使用验证 skill 检查改动，并提交截图或录屏作为证据；
- **性能优化**：先采集现状 trace，再做针对性修改，最后用多次运行确认收益；
- **回归验证**：并行启动多个 Agent 执行验证，扩大样本量或对关键路径做 fuzz；
- **用户反馈**：自动监听反馈渠道，让 Agent 先尝试复现；如果 verification skill 和 Feature Map 足够好，再考虑自动修复。

这里的关键不是“让更多 Agent 同时写代码”，而是让每个 Agent 都能独立完成、独立验证，并把可审阅的证据交还给人。

## 八、像维护基础设施一样维护 harness

Repo harness 不是一次性搭建完就结束的东西。功能会变化，入口会变化，验证方式也会变化。Feature Map、验证 CLI、lint 和测试都需要像基础设施一样持续维护。

poteto 建议至少每天运行一次维护 verification skill 的任务，让 Agent 始终拿到控制应用的最新方式。对团队来说，甚至可以为它设置 oncall。

具体可以这样做：

- 定期检查 Feature Map 是否和真实应用一致
- Agent 修改功能入口时，同步更新 Feature Map 和验证命令
- 验证 CLI 本身也要有测试
- 重复出现的问题，沉淀成 lint、类型约束或验证命令
- 有人对 harness 的健康负责，而不是等它慢慢失效

poteto 在 Grok Bot 中扮演的角色，很像是一个代码库园丁：持续监控代码、重构、增加新的 lint 和检查，同时开发功能。代码库质量是在持续修剪和加固中维持的。

## 九、从今天开始建设 repo harness

如果你要从今天开始建设 repo harness，可以按这个顺序：

1. 写清楚应用入口、功能入口和模块边界；
2. 把关键约束变成类型、lint 和测试；
3. 为每个任务写清楚目标、非目标和完成标准；
4. 做一个 Agent 可调用的开发 / 验证 CLI；
5. 建立 Feature Map，记录功能入口和验证方式；
6. 要求 Agent 提交 PR 时附带证据；
7. 当单个 Agent 可以稳定闭环后，再增加并行和自动化；
8. 持续维护 harness，让它跟上代码库的变化。

提高 AI 编程产出的关键，不是让人更快地 Review 更多 PR，而是让仓库本身能告诉 Agent：

- 这里有什么；
- 什么不能动；
- 这次要做什么；
- 怎样证明你做对了。

当这四个问题都能被仓库回答时，Agent 才能在真实工程中既快，又不把代码库写坏。
